# إدارة الملاعب — Stadium Booking

نسخة محلية مبنية على التطبيق المرفق، باستخدام React 18 وVite وFirebase. معرف المنتج هو `my-stadium-app-v1`. تم تنفيذ نقطة التحقق الأمنية الأولى؛ لم يتم نشر أي شيء أو تغيير إعدادات المشروع الحقيقي `malaebapp-d6409`.

## التشغيل

المتطلبات: Node.js 22.12 أو أحدث، Java 21 أو أحدث، وpnpm. يستخدم الإنتاج Node 22 للـFunctions. تحقق محلياً هنا باستخدام Node 24.19 وJava 25؛ يجب إعادة الاختبارات على Node 22 في بيئة النشر.

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm --dir functions install --frozen-lockfile --ignore-scripts
```

حزم المنصات الثنائية الخاصة بـesbuild وsharp مثبتة كاعتماديات؛ تأكد من عدم استبعاد optional dependencies. النسخ المختبرة مثبتة في ملفي `pnpm-lock.yaml`.

في نافذة طرفية أولى:

```sh
pnpm emulators
```

وفي نافذة ثانية:

```sh
pnpm dev
```

أو لتشغيل النسخة المبنية التي تم التحقق منها:

```sh
pnpm build
pnpm preview
```

الرابط المعتاد للمعاينة هو `http://127.0.0.1:4173`. الإعدادات الافتراضية محلية بالكامل، ولا تتطلب مفتاحاً أو حساب خدمة. يمكن نسخ `config/firebase.local.example` إلى `.env.local`. الاتصالات هي Auth:9099، Firestore:8085، Storage:9199، Functions:5001. البيانات مؤقتة وتختفي عند إيقاف المحاكيات ما لم تستخدم خيارات الاستيراد والتصدير الخاصة بـFirebase.

ملاحظة البيئة الحالية: منع Windows sandbox أداة esbuild من استكشاف المجلدات الأعلى أثناء تحسين اعتماديات خادم التطوير. بناء الإنتاج بـ`--configLoader native` ومعاينته يعملان وتم اختبارهما في المتصفح. لا يعني ذلك نجاح خادم التطوير داخل هذا العزل. يمكن تشغيل الأوامر من طرفية محلية عادية؛ لا يلزم تخفيف قواعد Firebase.

## تجربة المستخدم

1. اختر «حساب جديد» وأدخل بريد اختبار وكلمة مرور. في المحاكي تُطبع رسالة تأكيد البريد ورابطها في الطرفية، ولا يرسل بريد حقيقي.
2. افتح رابط التأكيد ثم اضغط «تحققت من البريد». الإدارة تتطلب توكن حديثاً يؤكد البريد.
3. أنشئ مباراة برمز اختياري أو رمز عشوائي، واضبط الموعد والمقاعد والتكلفة.
4. افتح رابط المباراة من متصفح آخر، واختر «متابعة كلاعب» ثم سجل الاسم والمركز والمستوى. التسجيل لا يتطلب بريداً.
5. إيصال الدفع صورة PNG/JPEG/WebP بحد أقصى 700 كيلوبايت. يراجعه اللاعب نفسه أو مالك المباراة أو المشرف العام فقط.

التاريخ والموعد النهائي يُخزنان كـFirestore Timestamp (UTC)، ويُعرضان وفق المنطقة الزمنية للجهاز التي تظهر بجانب الموعد. إدخال التاريخ المحلي يتحول إلى لحظة زمنية واحدة؛ لا تُجمع سلسلة التاريخ مع تاريخ كامل آخر. الخادم وحده يحكم انتهاء مهلة الانسحاب.

هوية اللاعب المجهول مرتبطة بحساب Firebase في المتصفح وليست اسمه. مسح بيانات المتصفح أو تغيير الجهاز يفقد التحكم بالتسجيل؛ لا يمكن استرجاعه بالاسم. إنشاء حساب جديد أثناء الجلسة المجهولة يربط بيانات الدخول بالهوية نفسها. الدخول إلى حساب موجود مختلف لا يدمج الهويتين. يستطيع المشرف إزالة التسجيل القديم؛ لا تُنقل ملكيته اعتماداً على ادعاء اللاعب.

## نموذج الأمان والبيانات

| المسار | المحتوى والصلاحيات |
|---|---|
| `matches/{code}` | تفاصيل المباراة المنشورة، `ownerUid` ثابت، حالة المباراة وتسلسل التسجيل. يمكن قراءة مباراة مفتوحة بالرمز؛ لا توجد قائمة عامة بالمباريات. |
| `matches/{code}/players/{uid}` | الاسم والمركز والمستوى وحالة أساسي/احتياط. القراءة تتطلب تسجيل الدخول. لا توجد معلومات دفع هنا. |
| `matches/{code}/payments/{uid}` | حالة الدفع ومسار الإيصال؛ للمالك والمشرف العام واللاعب المعني فقط. |
| `matches/{code}/private/paymentInfo` | تعليمات الدفع النصية؛ للمسجلين والمشرفين فقط. |
| `proofs/{code}/{uid}/{random}.png` | إيصال معاد ترميزه؛ لا توجد روابط تنزيل دائمة أو download tokens. |
| `cleanup/{job}` | مهام حذف ملفات داخلية؛ لا وصول من العميل. |

جميع كتابات Firestore المباشرة مرفوضة حتى للمالك. بديلها Functions callable تتحقق بصورة مستقلة من Firebase Auth، تأكيد البريد، ملكية المباراة أو claim موثوق، وقوائم الحقول المسموح بها. Admin SDK يتجاوز القواعد، لذلك فحص الصلاحيات داخل كل handler ضروري. ليست واجهة المشرف حدّ الأمان.

المعاملات ترتب التسجيلات بتسلسل يصدره الخادم، وتمنع تكرار UID، وتعيد توزيع الأساسي والاحتياط عند الانسحاب أو تغيير السعة. الحد 100 لاعب أساسي و200 تسجيل إجمالي لكل مباراة، لإبقاء عمليات المعاملة والمسح ضمن الحدود. إضافات المشرف اليدوية لها هويات `manual-*` ولا يمكن للاعب ادعاء ملكيتها أو رفع إيصال عنها.

رفع Storage المباشر مرفوض للجميع عمداً. تمر الصورة عبر callable بحجم محدود؛ يتحقق sharp من المحتوى والنوع وعدد البكسلات، ثم يعيد ترميزها إلى PNG مع إزالة metadata. Base64 يستخدم فقط لنقل الطلب/الاستجابة ولا يُخزن في Firestore. تنزيل الإيصال داخل التطبيق يتم بطلب مصادق، وتتحقق قواعد Storage أيضاً من هوية القارئ والمسار الحالي. استبدال إيصال يبطل الوصول إلى المسار القديم فور تغيير مرجع الدفع.

## الحذف والتنظيف

حذف المباراة يضعها أولاً في حالة `deleting` تمنع العمليات، ثم يحذف ملفاتها ومجموعاتها الفرعية، ويترك tombstone باسم الرمز حتى لا يتداخل حذف قديم مع مباراة جديدة. إذا فشل الحذف تظهر إعادة المحاولة في لوحة المالك. الانسحاب ومسح القائمة ينشئان مهام تنظيف دائمة؛ تصبح الملفات القديمة غير قابلة للوصول فوراً، ويزيلها مشغل موثوق لاحقاً:

```sh
node scripts/cleanup.mjs PROJECT_ID STORAGE_BUCKET
```

شغّل هذه الأداة يومياً باستخدام Application Default Credentials بصلاحيات محددة؛ لا تضع مفاتيح الخدمة في المشروع. تنظف المهام والملفات اليتيمة الأقدم من 24 ساعة. لم يتم إعداد مجدول إنتاج أو تشغيل الأداة ضد الإنتاج. قبل حذف مستخدم من Firebase Auth، أزل تسجيلاته عبر المشرفين/العمليات الموثوقة لتحرير المقاعد وترقية الاحتياط، وتعامل مع مبارياته المملوكة، ثم احذف حساب Auth وشغل التنظيف. حذف حساب Auth وحده لا يحذف بيانات Firestore أو الملفات تلقائياً.

## الاختبارات

```sh
pnpm test
# أوقف المحاكيات الموجودة أولاً؛ هذا الأمر يشغل مجموعة مستقلة ويوقفها بعد الاختبار:
pnpm test:security
# أو إذا كانت المحاكيات تعمل مسبقاً:
pnpm test:integration
pnpm build
```

الاختبارات تستخدم المشروع التجريبي فقط. `tests/security.test.mjs` يختبر Auth وFirestore Rules وStorage Rules وFunctions الحقيقية محلياً، بما في ذلك طلبات متزامنة. رفض العمليات المتعمد يظهر أحياناً كـPERMISSION_DENIED في السجل؛ النتيجة النهائية للاختبار هي المرجع. انظر `verification/security.txt` و`verification/unit.txt` و`verification/build.txt` و`verification/REPORT.md`.

## إعداد المشروع الحقيقي قبل أي نشر

لم تتوفر جلسة Console موثوقة لفحص إعداداته الفعلية. يجب مراجعة المشروع الموجود قبل التعديل، بما يشمل Firestore location وStorage bucket وAuth providers والـauthorized domains وIAM والفوترة المطلوبة لتشغيل Functions/Storage. لا تُنشئ مشروعاً بديلاً ولا تكتب فوق إعدادات موجودة دون مراجعتها.

- فعّل Email/Password وAnonymous Auth، واضبط سياسة كلمة المرور ومحتوى رسائل التأكيد والاستعادة ونطاقات الرجوع.
- تحقق من اسم حاوية Storage الفعلي؛ الاسم الموجود في المصدر المرفق هو `malaebapp-d6409.firebasestorage.app`. تأكد أن حاوية Admin SDK الافتراضية هي نفسها.
- ضع إعداد Firebase Web العام في `.env.production`، مع `VITE_USE_EMULATORS=false` ومعرف المشروع الصحيح وكل متغيرات `config/firebase.local.example`. إعداد Web ليس حساب خدمة؛ لا تضع أسرار Admin SDK في متغيرات VITE.
- راجع القواعد الحالية المفتوحة واستبدلها بالقواعد المرفقة عند النشر المصرح، قبل توجيه أي مستخدم حقيقي للنسخة الجديدة. جميع مسارات `artifacts` القديمة مرفوضة افتراضياً في القواعد الجديدة.
- راجع أدوار Service Account، وتمكين صلاحية وصول Storage Rules إلى Firestore عند طلب Firebase ذلك، وخطة التنظيف والمراقبة وحدود الاستخدام. App Check ومكافحة إنشاء هويات مجهولة متعددة ليست مُفعّلة في هذا التسليم؛ الواحدية هنا لكل UID، وليست ضماناً لهوية الشخص الحقيقي.
- تحقق من Node 22 في CI وأعد تشغيل الاختبارات. لا تعتمد على المحاكيات لإثبات IAM أو الفوترة أو تسليم البريد أو سلوك الإنتاج.

## المشرف العام

لا يوجد مفتاح رئيسي أو صفحة تمنح الصلاحيات. بعد التحقق من المستخدم وبريده، ينفذ مشغل موثوق فقط:

```sh
node scripts/admin.mjs malaebapp-d6409 USER_UID grant
node scripts/admin.mjs malaebapp-d6409 USER_UID revoke
```

تستخدم الأداة Application Default Credentials خارج ملفات العميل، وتحافظ على claims الأخرى. بعد المنح يجب تحديث ID token أو إعادة الدخول. إلغاء الصلاحية يبطل refresh tokens، لكن ID token الصادر قد يستمر حتى ساعة؛ ضع ذلك في إجراء الاستجابة للحوادث. لا تستخدم هذه الأداة في المتصفح.

## البناء والنشر

```sh
pnpm build
# فقط بعد مراجعة الإعدادات والحصول على موافقة صريحة على النشر:
pnpm exec firebase deploy --project malaebapp-d6409 --only firestore:rules,firestore:indexes,storage,functions,hosting
```

هذا الأمر توثيق فقط؛ لم يتم تنفيذه. لا يوجد alias افتراضي للإنتاج. Hosting يعيد الروابط إلى `index.html`، وتستخدم روابط المباراة `?id=...` مع دعم التحديث والرجوع في المتصفح.

## حدود نقطة التحقق

احتُفظ بتدفقات المباراة والمشاركة والقائمة والانتظار والدفع والفرق وإدارة اللاعبين. بيانات الدفع أصبحت نصاً خاصاً بدلاً من صورة عامة؛ رفع صورة تعليمات الدفع واستعادة سجل الزيارات المحلي والتنظيف الجماعي للمباريات مؤجلة للتحقق الوظيفي التالي. حالة الدفع لم تعد منشورة لجميع اللاعبين، بل تخص اللاعب والمشرفين. لا يوجد تغيير بصري شامل أو توسع ميزات بعد نقطة التحقق.

مراجع التنفيذ: [اختبار قواعد Firestore](https://firebase.google.com/docs/firestore/security/test-rules-emulator)، [Callable Functions](https://firebase.google.com/docs/functions/callable)، [تشغيل Functions محلياً](https://firebase.google.com/docs/functions/local-emulator).
